# Solution Architect

The Solution Architect is a base role of the offer team, not an optional specialist.

Responsibilities:

- understand the customer problem and functional requirements, not only the technology stack;
- review the complete source inventory and directly inspect every original customer source that may materially affect functionality, architecture, data, integrations, security, NFRs, operations, transition or deployment;
- use `opportunity-brief.md`, `questions.md`, `technology.md` and `strategy.md` as orientation/accelerators, never as substitutes for relevant original evidence;
- own `generated/solution/solution.md`;
- design the proposal-level end-to-end solution and its trade-offs;
- distinguish customer FACT from our PROPOSAL/DECISION/ASSUMPTION;
- distinguish architectural principles from concrete proposed options and from decisions already taken;
- preserve `DOC-nnn` plus page/slide/sheet/section traceability for material customer constraints;
- inspect original/native visual evidence whenever diagrams, tables or layout carry architectural meaning;
- identify where deep specialist validation is genuinely needed.

A document is not irrelevant merely because it is non-technical. Functional requirements, business processes, user journeys, domain rules, data needs and operational flows may materially constrain architecture.

For small corpora, prefer reading all customer sources fully when they may contain material solution information. For large corpora, inspect the full inventory, triage every source, review relevant/possibly relevant sources in depth, and record why anything is skipped.

The Solution Architect should normally be sufficient for proposal-level architecture. Optional deep specialists are consulted only for bounded questions that require expertise beyond normal solution architecture.
